## 失敗1: コース変更で「現学年のコース表」が取れず迷走した (2026-05-22)

### 状況
学年が進級した既存生（現在高2 / 入会時小6 / 2021年入会。seitocdは伏せる）を
「国数英 週3 → 数学のみ 週1」にコース変更する作業。
正しい高2のコース（PS2･高2＝コード12100 / 単価20,220）になかなか辿り着けなかった。

### 症状
- `sks_jugyo_register` が `PS2標準コースを自動特定できません（学年=高2）` で停止。
  `available_courses` には **小6** のコース（11100:PS1･小6 / 12100:PS2･小6 …）しか出ない。
- ブラウザから直接 `IF2SHOW|{seitocd}|01|{nyujukudt}` を叩いても **小6** のコース表しか返らない。
- 通番(rowno)を 00/01/02/03、日付を 20260522 に変えて何度叩いても全部小6。

### 何をそんなに迷っていたか（誤った思考の流れ）
1. 「コース表の学年は入会日(imnyujukudt=2021)基準で決まる」と思い込んだ。
   → JSを読むと確かに `IF2SHOW|seitocd|tsuban|imnyujukudt` で imnyujukudt を渡していたので、
     「GUIでコース変更しても小6が出るはずだ」と誤結論。
2. 「コードはgrade-generic（12100=PS2で学年非依存）、価格はサーバー側で現学年から再計算される」
   という**誤った仮説に逃げた**。
   → だが当該生の現額 57,230（国数英週3）は 小6単価16,770×3=50,310 を超えるので、
     この仮説では説明がつかない（高2には固有の高い単価がある）と分かっていたのに深追いした。
3. 「別の高2在学中に入会した生徒からなら高2単価が取れる」と回り道を検討し始めた。

### 真因
**GUIの正規の操作順序を飛ばして、いきなり読み取りAPI(IF2SHOW)を叩いていた。**

SKSのコース表の学年は「入会日」ではなく「**いま編集対象にしている受講履歴行（通番tsuban）の適用日**」で決まる。
学年進級した既存生の場合：
- 入会時通番(tsuban=01)を見る → **入会時学年（小6）**のコース表
- コース変更日(2026/05/22)の履歴行を**新規に追加**して発番された**新通番(tsuban=08)**を見る
  → **適用日時点の学年（高2）**のコース表（PS2･高2=12100 / 単価20,220 が出る）

ユーザーの「追加を押して登録してから、教科を登録するんだよ」の一言が正解だった。

### 正しいやり方（GUI / AJAX 共通）
1. 受講履歴行を**先に登録**する（これが新通番を発番する）
   `IF1regist|{seitocd}|{lasttsuban}|{nyujukudt}|{適用日YYYYMMDD}|{rireki=05}|`
   → 新しい通番（例: 08）が発番される
2. その**新通番**でコース表を引く
   `IF2SHOW|{seitocd}|{新通番}|{nyujukudt}`
   → 適用日時点の学年のコース一覧＋TANKA/WGK が返る
3. コースを確定する
   `IF2ADD|{seitocd}|{新通番}|{nyujukudt}|{行}`
   行 = `{idx}:{コードcd}:{回数}:{国}:{数}:{英}:{理}:{社}:{金額}`
   例: `0:12100:1:0:1:0:0:0:20220`（PS2･高2 / 週1 / 数のみ / ¥20,220）

実測の発番列（当該生の例）:
```
IF1regist|{seitocd}|07|{nyujukudt}|20260522|05|
IF2SHOW|{seitocd}|08|{nyujukudt}          ← 新通番08で高2コース表
IF2ADD|{seitocd}|08|{nyujukudt}|0:12100:1:0:1:0:0:0:20220
```

### 教訓
1. **SKSの読み取りAPIも前段の状態（履歴行・通番）に依存する。** 状態を作らずに読むと古い/誤った結果が返る。
   「読むだけだから安全」と近道せず、人間がGUIでやる操作順序を素直に再現する。
2. 学年進級した既存生のコース変更は、**入会時通番のコース表＝入会時学年**。
   新通番を発番してはじめて現学年（適用日学年）が出る。
3. これが `sks_jugyo_register` の「PS2標準コース自動特定できません」の真因。
   → ツール改善案: rireki が 02以外（05コース変更/06選択科目変更/再登録）のときは、
     先に IF1regist で履歴行を追加→新通番を取得→その通番で IF2SHOW を引く実装にすべき。
     現状は入会時通番ベースで IF2SHOW を引くため、進級済み生で学年が合わない。
4. 仮説が現データ（当該生の57,230）と矛盾していたのに深追いした。
   **矛盾に気づいたら仮説を捨てて、正規フローの再現に戻る。**

### 確定値メモ（高2 PS2）
- コード `12100` = PS2･高2 / 単価 **20,220**
- 割引(WGK): 週1=0 / 週2=2,290 / 週3=3,430
- 検証: 20,220×3 − 3,430 = **57,230**（当該生の旧 国数英週3 と一致）
- 数学のみ週1 = 20,220×1 − 0 = **20,220**
- ※ 単価は学年・改定で変わる。常に新通番の IF2SHOW から取り直すこと（値を埋め込まない）。

## 失敗2: IEB070 振込者／WN請求者の分類が実態と乖離 (2026-05-28)

### 状況
教室長から「IEB070（振込者用料金入力）の **振込者リスト** と **WN請求者リスト** がバグっている」との指摘。
過去にも同様の修正を行った記憶があるが再発しており、いつ書き換わったか分からないとのこと。
seitocd・教室コードは伏せる。

### 症状
- IEB070 `seitoshubetsu=0`（振込者）リストに、SKS代金内訳明細書(IEB551a 生徒別合計)では **WN分類**で請求されている生徒が**6名**混入。
- 同 `seitoshubetsu=1`（WN請求者）リストに、実態は**振込運用**で口座情報も空の生徒が**1名**混入。
- いずれの生徒も「自分で支払い方法を変更した覚えはない」「IEB010を保存した覚えはない」状態。

### 調査の流れ
1. IEB070 を `?mode=sel&p={shubetsu}:::0` でGETしてリスト本体（`<div id="lay0">` 内）をパース。
   ※ POSTで `seitoshubetsu` だけ送ってもリストはレンダリングされないので注意。
2. SKS代金内訳明細書(`IEB550.wpp` → `bizreport.pl` 経由PDF)の対象月の教室計・生徒別を取得して付き合わせ。
3. 不一致のあった生徒について `sks_internal_get_fields` で関連フィールドを取得。

### 真因（推定）
IEB070 のフィルタ振り分けは、**IEB010 の `imwnstym`（WN開始年月、画面表示用 YYYY/MM）が値か空か**で判定している。
一方、実際の請求時の支払方法（WN/振込）は **`wnkozakb`**（WN口座区分）等の別フィールドで決まる別系統。

両者が同期して更新されないため、片方だけがリセット/設定漏れになると IEB070 の振り分けと実請求方法が乖離する。
**`imwnstym` 側だけが空に書き換わる**事象が一斉に発生する模様（影響生徒6名が揃って空白だった）。

書き換わりの直接的なログはSKS側で公開されておらず、変更履歴を見るAPI/画面は未発見。
状況証拠としては、**進級処理／コース変更の新通番(tsuban)発番**（失敗1で扱った操作）の副作用、
あるいは月次のWN締済処理の副作用が疑われる。

### 検証データ（観察された不整合パターン）

| パターン | `wnkozakb` | 銀行口座 | `imwnstym` | IEB070分類 | SKS明細実態 |
|---|---:|:---:|:---:|:---:|:---:|
| 正常(WN) | 1 | あり | 値あり | WN | WN |
| 異常① | 1 | あり | **空** | 振込 ⚠ | WN |
| 異常② | 2 | なし | **空** | 振込 ⚠ | WN（口座なしでWN？別問題） |
| 異常③ | 3 | なし | **値残留** | WN ⚠ | 振込（過去はWN登録あり） |

→ フィルタが `imwnstym` のみを見ているため、`wnkozakb` や口座情報の有無と整合しなくても気付けない。

### 正しいやり方（修正手順）
1. **IEB070 の両リスト** を `?mode=sel&p=0:::0` / `?mode=sel&p=1:::0` で取得し、各生徒コードを抽出。
2. 各生徒の `sks_internal_get_fields` で `wnkozakb` / 口座情報(`ZenginCD`,`KozaNO`) / `imwnstym` / `imnyujukudt` を取得。
3. 実態の請求区分（SKS代金内訳明細書 IEB551a の区分列：WN / カード / 振込）と突き合わせる。
4. 不整合があれば `sks_internal_update_fields` で修正:
   - **WN運用にしたい生徒**: `imwnstym` = YYYY/MM、`wnstym` = YYYYMM（両方必須）
     - 開始月が分からなければ入塾月（`imnyujukudt` の年月）で代用
   - **振込運用にしたい生徒**: `imwnstym` = `""`、`wnstym` = `""`
5. 修正後 IEB070 を再取得して、対象生徒がリストを移動したことを確認。

#### `sks_internal_update_fields` の注意
- `imwnstym` 単独でPOSTしても永続化されない場合がある（`before`/`after` が空のまま返ってくる）。
  **必ず `imwnstym` と `wnstym` を同時に送る**こと。
- 設定の場合: `{"imwnstym": "2025/04", "wnstym": "202504"}`
- 削除の場合: `{"imwnstym": "", "wnstym": ""}`
- レスポンスの `result` は `UNKNOWN` でも更新は反映されている（再GETで確認すること）。

### 教訓
1. **IEB070 の表示振り分けと実請求区分は別系統**。`imwnstym` の有無＝WN運用ではない。
   発見方法は「IEB070のリストとIEB551a教室計の区分突合」が確実。
2. **`imwnstym` は意図せずリセットされる**。誰の保存操作でもなく、進級・コース変更等の副作用で消える疑いがある。
   そのため修正しても再発する。**月次（特に進級時期・年度切替直後）に整合性チェックを回す運用**を推奨する。
3. 直接の変更履歴がSKSにないので、原因の決定的特定はサポート問い合わせ（フランチャイズ総合受付）が必要。

### 自動整合性チェックの設計案（未実装）
- 入力: IEB070 振込者/WN請求者リスト
- 各生徒について以下を取得・突合:
  - `wnkozakb`（1/2=WN、3=振込）
  - 銀行口座情報の有無
  - `imwnstym` の有無
  - 直近のSKS代金内訳明細書の区分（WN/カード/振込）
- 出力: 不整合のある生徒リスト＋推奨修正アクション（imwnstym セット or クリア）
- 定期実行: 月初／20日締直後／4月進級直後

## 失敗3: 内部生の重複チェックを飛ばして二重 seitocd を発番した (2026-08-07)

### 状況
既に手動登録済（seitocd=260020、2026-08-05 登録、保護者・備考・クラブ会員 全部入り）
の中3生の入会依頼で `sks_naibusei_register_from_inquiry` を実行し、
seitocd=260021 を新規発番。同姓同名の二重レコードが発生。
さらに 260021 は生年月日を誤登録（正: 2011/04/02 早生まれ → 誤: 2010/04/02）。
260021 はユーザーが SKS 画面から手動削除して復旧。

### 症状
- 同一の（氏名・住所・電話・保護者）の内部生レコードが 260020 と 260021 の2件並存
- 260021 は生年月日が1年ズレ・保護者氏名/備考が空欄
- IEV120 コンビニ振込用紙、GDLS 連携、SafetyMail 登録、Googleコンタクト等の
  下流タスクがどちらの seitocd を参照するか不定になり得る状態

### 何をそんなに迷っていたか（誤った思考の流れ）
1. ユーザーが「外部生→内部生に登録して」と言った → 「外部生ルート」と「問合せルート」だけを
   チェックすれば十分と判断した（＝ユーザーの言葉尻に引っ張られた）
2. `sks_student_list(kubun="gaibu", name="加藤")` → ヒットせず（別人の 加藤優翔 のみ）
3. `sks_inquiry_search(name="加藤")` → No 1219（加藤ゆり子）ヒット → 問合せ直登録ルート採用
4. **`sks_student_list(kubun="naibu", name="加藤", include_taijuku=True)` を引かないまま実行**
5. 生年月日は「中3 なら 2010年生」で推測して 2010/04/02 を採用（4/2 は学年境界で
   早生まれと通常生まれが割れる日なのに考慮せず）

### 真因
**既にナレッジ（`sks_pcs.html` file21）に「SKS既存登録チェックは内部生＋外部生＋退塾者の
3パターン」の明示ルールがあった** のに、実行前に読まなかった／記憶から呼び出せなかった。
外部生と問合せの2つだけ引いて OK と判断したのは、ルール参照漏れによる自己流判断。

生年月日ミスの真因は「学年から年を推測」＝file21 とは別の推測禁止ルール違反
（work_rules.md「推測情報は書くより無い方がマシ」）。既存内部生レコード（260020）に
実生年月日（2011/04/02）があったので、そもそも内部生チェックを引いていれば発覚した。

### 正しいやり方（新規内部生 登録前の チェックリスト）
```
sks_student_list(kubun="naibu", name="姓のみ", include_taijuku=True)   # ← これが今回抜けた
sks_student_list(kubun="gaibu", name="姓のみ")
sks_inquiry_search(name="姓のみ")
```
- **フルネームで 0件なら 姓のみで再検索**（全角/半角スペース違いでヒット率が変わる）
- 内部生名簿に同姓同名がいたら **登録を止めてユーザーに確認**（同一人物か別人かは AI では判定不可）
- 同一人物と判明したら 新規登録せず、既存 seitocd の `sks_internal_update_fields` で
  差分のみ更新する（入塾日・キャンペーン・引落開始年月 等）
- 生年月日は 用紙に明記された年をそのまま使う。用紙に月日のみの場合、
  **4/1 と 4/2 は早生まれ／通常生まれで年が割れる** ので学年からの推測禁止。
  既存レコード（内部生／外部生／兄弟）との突合、あるいはユーザー確認で確定させる

### 教訓
1. **ナレッジにルールが既にある可能性を先に疑う**。SKS 生徒登録系の判断をする前に、
   最低限 `sks_pcs.html` の pagetoc を眺めて 該当エントリを引く。読まずに走ると
   既に文書化されている落とし穴に必ず落ちる
2. **ユーザーの言葉尻（「外部生→内部生」）を SKS 状態の推定に使わない**。
   ユーザーのメンタルモデルと 実際の SKS レコード は 別物。一次ソース（内部生名簿）
   を確認してから動く
3. **不可逆な書き込み操作の前には dry_run＋人間確認 を挟む慣行を守る**。
   今回 dry_run は挟んだが、その前段の「既存チェック」を飛ばしたので dry_run が
   意味を成さなかった（重複と気付ける情報が dry_run preview に無い）
4. ツール改善案: `sks_naibusei_register_from_inquiry` / `sks_convert_gaibu_to_internal` の
   内部で「同姓同名の内部生が既にいる場合は `DUPLICATE_WARNING` を返して停止」を
   実装するべき。現状は氏名の重複を全くチェックせずに新 seitocd を発番してしまう
